# review: リポジトリ固有のレビュースキルで指摘を出し、difit に投稿する

## 前提

- `session.json` が存在し、difit が起動していること。無ければ `phases/start.md` から。
- `session.json` の `review_skill` にスキル名があること。無ければ start と同じ基準で決め、`phases/start.md` の手順 5 で session.json に書く。

## 手順

### 1. レビュー範囲を決める

| 状況 | 範囲 |
| --- | --- |
| 初回、または PR 作者が修正した後 (ケース 1) | `base_sha..head_sha` の PR 全体 |
| ケース 2 で自分が指摘対応のコミットを積んだ後 | `reviewed_head_sha..HEAD` の差分のみ |

`reviewed_head_sha` は前回のレビュー時の head であり、session.json に入っている。null なら初回である。
ケース 2 でコミットを積んだ後は、先に `scripts/sync.sh <state-dir>` を実行して difit と session.json の head を新しい HEAD に合わせる。

### 2. リポジトリ固有のレビュースキルを実行する

Skill ツールでスキルを起動する。スキルは現在のディレクトリを対象にするので、`session.json` の `worktree` と一致していることを先に確認する。
差分のみをレビューさせたい場合は、そのスキルが対応している引数で範囲を渡す
(コミット群やベースコミットを指定する引数を持つスキルが多い)。対応していなければ、
プロンプトで「次のコミット範囲だけを対象にしてください」と明示する。

リポジトリ固有のスキルは多くの開発者が共有しているので、**このスキルの都合で変更しない**。
出力形式が何であれ、次の手順で変換する。

### 3. 指摘を findings JSON に変換する

スキルのレポートを読み、`reference/findings.schema.json` の形式に変換して `<state-dir>/findings-<日時>.json` に書く。

- `file` はリポジトリルートからの相対パス。
- `line` は指摘対象の行。範囲なら `{"start","end"}`。行を特定できない全体的な指摘は、PR 本文や設計に関するものなので difit には投稿せず、ユーザーへの報告に含める。
- `side` は追加・変更行なら `new`、削除された行への指摘なら `old`。
- `perspective` はスキルが使っている観点名をそのまま使う。観点の無いスキルなら指摘の種別 (例: `バグ`、`命名`) を短く付ける。
  再レビュー時に「同じ箇所・同じ観点」を判定する鍵になるので、毎回同じ語を使うことが重要である。
- `summary` は 1 行の要約。`body` は difit に表示する本文で、根拠と修正案を含める。

### 4. ユーザーの指示で実装した変更を覆す指摘を除く

ケース 2 では、再レビューの対象が「ユーザーが difit 上で指示し、Claude が実装した変更」そのものになる。
リポジトリ固有のレビュースキルはその経緯を知らないため、指示どおりに実装した変更に対して「元へ戻す」「なぜこの形にしたのか」という指摘を出す。
これを difit に投稿すると、ユーザーは自分が決めたことを Claude から問い直される。同じ論点の指摘と修正が往復し、レビューが収束しない。

投稿の前に、ユーザーの指示で実装した変更の一覧を取得する。

```bash
python3 $SKILL_DIR/scripts/state.py directives --state <state-dir>/threads.jsonl
```

各レコードは、元の指摘 (`summary` と `body`)、ユーザーの指示 (`instruction`。`+` だけの返信なら空文字で、その場合の指示は元の指摘の修正案そのもの)、実装したコミット (`fix_commit`) を持つ。
手順 3 で作った指摘を 1 件ずつこの一覧と突き合わせ、次のどれかに当たる指摘には、findings JSON の `overrules` に該当レコードの `key` を書く。

- 修正案が、指示で実装した変更の取り消し、または変更前の形への復元になっている
- 指示で選んだ方針と逆の方針を勧めている (例: 「A に合わせて」という指示で A に合わせた箇所へ、「B に合わせるべき」と指摘する)
- 指示で実装した変更について、その形を選んだ理由や判断の背景を尋ねている

`overrules` を書いた指摘を `difit-post.sh` は投稿せず、対応不要として記録する。**「この変更はユーザーの指示に基づきます」という注記を本文に足して投稿する方法は取らない。** 注記を付けても、ユーザーが決めたことを問い直す点は変わらない。

判断の基準:

- **指示の範囲を広く取る。** 「A に合わせて」という指示は、指摘が挙げた箇所だけでなく、その PR が持ち込んだ同種の箇所すべてに及ぶ (`phases/triage.md`「同じ修正が必要な他の箇所も探す」)。指示どおりに揃えた結果として生じた性質 (合わせた先が持つ非効率や書き方の癖) への指摘も、指示を覆す指摘として扱う。
- **指示を維持したまま直せる指摘は投稿する。** 指示で実装した変更が持ち込んだ不具合 (誤った計算結果、panic、データの破損、コンパイルやテストの失敗) と、指示どおりに揃える作業の漏れ (揃え残した箇所、揃えた箇所どうしの不一致) は、指示と矛盾しない。`overrules` を書かずに投稿する。このとき修正案は指示を維持する形で書き、変更の取り消しを選択肢に含めない。
- **迷ったら投稿しない側へ倒さない。** 指示と指摘の関係を説明できないなら `overrules` を書かずに投稿する。`overrules` は「この指摘に従うと、どの指示で実装したどの変更が無くなるか」を具体的に言えるときだけ書く。

`overrules` を書いた指摘は、件数と 1 件 1 行の要約 (どの指示を覆す指摘だったか) を手順 7 の報告に必ず含める。黙って捨てない。
ユーザーが報告を読んで方針を変えたいと考えたら、そのときに指示を出し直せる。

ケース 1 (他人の PR) には、ユーザーの指示で実装した変更が無いので、この手順は不要である。

### 5. 投稿する

```bash
$SKILL_DIR/scripts/difit-post.sh <state-dir> <findings.json>
```

出力の意味:

- `suppressed`: 同じ箇所・同じ観点で過去に判断済みのため投稿しなかった指摘。件数と過去の判断理由をユーザーに伝える。
- `annotated`: 同じ箇所だが観点が違う、または同じ関数内で同じ指摘が別の行に移った。過去の判断を注記して投稿した。
- `overruled`: `overrules` を書いたため投稿しなかった指摘。対応不要として記録済み。
- `posted`: 投稿した件数。

### 6. session.json を更新する

```bash
jq '.reviewed_head_sha = .head_sha' <state-dir>/session.json > /tmp/s.json && mv /tmp/s.json <state-dir>/session.json
$SKILL_DIR/scripts/phase-done.sh <state-dir> review
```

### 7. 報告

投稿件数、抑止件数、ユーザーの指示を覆すため投稿しなかった指摘 (件数と 1 件 1 行の要約)、difit の URL を伝える。ユーザーは difit 上で各指摘に対応要否を返信するので、
`reference/reply-convention.md` の書式 (`+` で対応、`-` で不要、`不要: 理由` で理由付き) を一言添える。
