# difit 上の返信書式

difit には resolved やラベルの概念が無いため、返信本文の先頭語で意思を表す。`scripts/state.py triage` はこの規則で分類する。

先頭語は 3 種類しかない。**`q` は Claude Code 宛て、`+` と `-` は対応要否の表明、どれも付いていない本文はレビュイー (PR 作者) へのコメント**である。

## Claude の指摘への返信

| 先頭語 | 意味 | 例 |
| --- | --- | --- |
| `q` | Claude Code 宛て。質問に限らず指示も含む | `q この記述は正しいですか？`、`q この指摘は取り下げて` |
| `+` | 対応が必要。続く文は補足として GitHub 投稿や実装に反映する | `+`、`+ ただしログは warn で` |
| `-` | 対応不要。続く文が理由になり、再指摘防止リストに残る | `-`、`- マイグレーション 0042 でバックフィル済み` |
| `対応` | `+` と同じ | `対応 ただしログは warn で` |
| `不要` | `-` と同じ | `不要: マイグレーション 0042 でバックフィル済み` |
| 上記以外 | レビュイーへのコメント。対応が必要なものとして Claude の指摘と一緒に GitHub へ投稿する | `ここは仕様の変更が必要では？` |

先頭語の後の `:` `：` 空白 タブ 改行は無視する。`q:` も `q ` と同じ扱い。
`q` `対応` `不要` は、後ろに区切り文字 (空白 `:` `：` タブ 改行) が続くか本文がそれで終わるときだけ先頭語として扱う。
`query が空のとき` や `不要な変数が残っている` のような語の先頭を誤認しないためである。
`+` と `-` は区切り文字を要求せず、本文の先頭 1 文字が一致すれば先頭語として扱う。
そのため箇条書きの `- 項目` や `+1` も対応要否と読むが、返信でその書き出しを使う場面が無いため許容する。全角の `＋` `－` `ー` も同じ扱い。

GitHub へ載せる本文からは先頭語を落とす (`+ ただしログは warn で` は `ただしログは warn で` として投稿する)。
レビュイーは対応要否の表明そのものを読む必要がないためである。

## ユーザーが新しく書くスレッド

| 書き方 | 意味 |
| --- | --- |
| `q ` で始まる | Claude Code 宛て。answer フェーズで応答する |
| それ以外 | ユーザー自身のレビューコメント。ケース 1 では GitHub の pending review に投稿し、ケース 2 では実装対象になる |

ユーザー自身のスレッドに、後からユーザーが `-` (`不要`) と返信すれば対応不要として扱う。

## `q` の本文はレビュイーに見せない

`q` で始まる本文はユーザーから Claude Code への質問や指示であり、レビュイーに見せるものではない。したがって次のように扱う。

- `q` の本文と Claude の応答は、GitHub の pending review に投稿する本文 (`github_body`) に含めない。
- 未処理の `q` が 1 件でも残っている間は、GitHub への pending 投稿に進まない。先に answer フェーズで応答する
  (`scripts/next.sh` は `to_claude` を `fix` や `user_finding` より優先する)。
- 応答を読んだユーザーが、続けて `+` や `-` を付けて対応要否を決める。
- ユーザー自身のスレッドの本文が `q` だけの場合、GitHub に投稿できる本文が無いので `github_body` は空になる。
  そのスレッドを GitHub の指摘にしたいときは、difit 上でスレッド本文をレビューコメントとして書き直す。

## 分類結果 (`difit-fetch.sh` の `classification`)

| 値 | 状態 |
| --- | --- |
| `fix` | 対応が必要。`text` に補足またはレビュイーへのコメント |
| `dismiss` | 対応不要。`text` に理由 |
| `to_claude` | 未処理の Claude Code 宛ての本文。`text` に `q` を除いた本文 |
| `pending` | Claude の指摘にまだ返信が無い |
| `user_finding` | ユーザー自身のレビューコメント |
| `github` | GitHub から取り込んだスレッドで、ユーザーの返信が無い |
| `none` | Claude が最後に発言しており、次の返信待ち |
| `processed` | 対応要否を処理済み。Claude の指摘とユーザー自身のスレッドのうち、状態ファイルの status が `posted` / `resolved` / `dismissed` のもの。返信を分類し直さない (処理した後に書いた `q` だけは `to_claude` になる) |

`processed` は、GitHub に投稿した後や実装した後のスレッドを分類し直さないための値である。
GitHub に投稿した後も、sync で作り直すまで difit には `+` の返信が付いた投稿前のスレッドが残る。作り直した後は、PR 作者の返信が付いた GitHub のスレッドが並ぶ。
これらを返信で分類し直すと、同じ指摘を重複して投稿したり、実装済みの指摘を再び実装したりする。そのため状態ファイルの status が処理済みなら、返信の先頭語を見ない。
処理した後の議論は GitHub で続ける。ただし処理した後に書いた `q` の本文には answer フェーズで応答する。

各スレッドには `github_body` も付く。GitHub の pending review に投稿するときの本文で、
Claude の指摘なら「ユーザーの返信 → `---` → Claude の指摘原文」の順に組み立ててあり
(`+` だけの返信、`q` の本文、再指摘防止の注記は除く)、ユーザー自身のスレッドなら本文そのままである。
ただし本文が `q` だけのスレッドは空文字列になる。先頭語 (`+` `-` `対応` `不要`) は取り除いてある。

## 理由をきちんと書く意味

`不要` の理由は、そのまま再指摘防止リスト (状態ファイル) に残る。次のレビューで Claude が同じ箇所を別の観点から指摘すると、`state.py to-difit` がその理由を注記として指摘の先頭に付ける。
「不要」だけでも動作するが、理由があると再判断の負荷がほぼ無くなる。
