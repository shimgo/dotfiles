# difit 上の返信書式

difit には resolved やラベルの概念が無いため、返信本文の先頭語で意思を表す。`scripts/state.py triage` はこの規則で分類する。

## Claude の指摘への返信

| 先頭語 | 意味 | 例 |
| --- | --- | --- |
| `対応` | 対応が必要。続く文は補足として GitHub 投稿や実装に反映する | `対応`、`対応 ただしログは warn で` |
| `不要` | 対応不要。続く文が理由になり、再指摘防止リストに残る | `不要: マイグレーション 0042 でバックフィル済み` |
| `質問` | Claude Code に聞きたい | `質問: この関数を分けずに済む方法はある？` |
| `q` | `質問` の省略形 | `q この記述は正しいですか？` |
| `+` | `対応` の省略形。本文が `+` 1 文字だけのとき | `+` |
| `-` | `不要` の省略形。本文が `-` 1 文字だけのとき。理由は残らない | `-` |

先頭語の後の `:` `：` 空白 タブ 改行は無視する。`@claude`、`Q:`、`q:`、`?`、`？` も `質問` と同じ扱い。
`q` は後ろに区切り文字 (空白 `:` `：` タブ 改行) が続くときだけ質問として扱う。`query が空のとき` のような語の先頭を誤認しないためである。
`+` と `-` は本文がその 1 文字だけのときにしか効かない。`- 項目` のような箇条書きや `+1` を誤認しないためである。
理由を残したいときは `不要: 理由` を使う。全角の `＋` `－` `ー` も同じ扱い。

## ユーザーが新しく書くスレッド

| 書き方 | 意味 |
| --- | --- |
| `質問:` または `q ` で始まる | Claude Code への質問。answer フェーズで返信する |
| それ以外 | ユーザー自身のレビューコメント。ケース 1 では GitHub の pending review に投稿し、ケース 2 では実装対象になる |

ユーザー自身のスレッドに、後からユーザーが `不要` と返信すれば対応不要として扱う。

## 質問の宛先は Claude Code であり PR 作者ではない

`質問` / `q` はユーザーから Claude Code への質問であり、PR 作者に見せるものではない。したがって次のように扱う。

- 質問の本文は GitHub の pending review に投稿する本文 (`github_body`) に含めない。
- 未回答の質問が 1 件でも残っている間は、GitHub への pending 投稿に進まない。先に answer フェーズで回答する
  (`scripts/next.sh` は `question` を `fix` や `user_finding` より優先する)。
- 回答を読んだユーザーが、続けて `+` や `-` を付けて対応要否を決める。
- ユーザー自身のスレッドの本文が質問だけの場合、GitHub に投稿できる本文が無いので `github_body` は空になる。
  そのスレッドを GitHub の指摘にしたいときは、difit 上でスレッド本文をレビューコメントとして書き直す。

## 分類結果 (`difit-fetch.sh` の `classification`)

| 値 | 状態 |
| --- | --- |
| `fix` | 対応が必要 |
| `dismiss` | 対応不要。`text` に理由 |
| `question` | 未回答の質問。`text` に質問本文 |
| `pending` | Claude の指摘にまだ返信が無い |
| `unclear` | 返信はあるが書式に合わない。ユーザーに確認する |
| `user_finding` | ユーザー自身のレビューコメント |
| `github` | GitHub から取り込んだスレッドで、ユーザーの返信が無い |
| `none` | Claude が最後に発言しており、次の返信待ち |

各スレッドには `github_body` も付く。GitHub の pending review に投稿するときの本文で、
Claude の指摘なら「ユーザーの返信 → `---` → Claude の指摘原文」の順に組み立ててあり
(`+` だけの返信、Claude Code への質問、再指摘防止の注記は除く)、ユーザー自身のスレッドなら本文そのままである。
ただし本文が Claude Code への質問だけのスレッドは空文字列になる。

## 理由をきちんと書く意味

`不要` の理由はそのまま再指摘防止リストに保存され、次のレビューで同じ箇所が別の観点から指摘されたときに注記として表示される。
「不要」だけでも動作するが、理由があると再判断の負荷がほぼ無くなる。
