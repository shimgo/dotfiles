# PR レビュー修正スキル

現在のブランチに関連するPRの未解決レビューコメントを取得し、妥当だと判断できる指摘を自動的にすべて修正する。1件ずつ修正可否を確認することはしない。

## ワークフロー概要

1. PR情報を取得する
2. レビューコメントを3種類すべて取得・表示する（Review thread / Review body / Issue comment）
3. 各指摘の妥当性を実コードで検証して判断する
4. 妥当な指摘をすべて自動的に修正する（事前確認なし）。同じ修正が必要な他の箇所も探して直す
5. 完了サマリーを提示する（自動修正しなかった指摘も理由付きで報告）

---

## Step 1: PR情報を取得する

```bash
# 現在のブランチ名を取得
git branch --show-current

# 現在のブランチのPR番号・URL・baseブランチを取得（baseはStep 4で差分の範囲を決めるのに使う）
gh pr list --head "$(git branch --show-current)" --json number,url,baseRefName --jq '.[0]'

# リポジトリのowner/nameを取得
gh repo view --json owner,name --jq '"\(.owner.login)/\(.name)"'
```

PRが見つからない場合は、ユーザーにPR番号を直接尋ねる。

---

## Step 2: レビューコメントを取得する

GitHubのPRには3種類のコメントがある。**必ず3種類すべてを取得する**こと。1種類だけ見ると見逃しが発生する。

| 種類 | フィールド | URL形式 | 解決状態の判定 |
|------|-----------|---------|----------------|
| Review thread (行コメント) | `reviewThreads.nodes` | `#discussion_rXXX` | `isResolved` で機械的に判定 |
| Review body (総評コメント) | `reviews.nodes.body` | `#pullrequestreview-XXX` | 解決の概念なし。bodyが非空なら対応要確認 |
| Issue comment (PR全体コメント) | `comments.nodes.body` | `#issuecomment-XXX` | 解決の概念なし。人のコメントは対応要確認 |

### 1回のクエリで3種類をまとめて取得する

`totalCount`が100を超える場合はページネーション（cursor）で全件取得する。

```bash
gh api graphql -f query='
query {
  repository(owner: "{owner}", name: "{repo}") {
    pullRequest(number: {pr_number}) {
      reviewThreads(first: 100) {
        totalCount
        nodes {
          isResolved
          comments(first: 20) {
            nodes {
              body
              author { login }
              path
              line
              url
            }
          }
        }
      }
      reviews(first: 100) {
        totalCount
        nodes {
          state
          body
          author { login }
          createdAt
          url
        }
      }
      comments(first: 100) {
        totalCount
        nodes {
          body
          author { login }
          createdAt
          url
        }
      }
    }
  }
}'
```

### 取得後の処理

**1. Review thread (行コメント)**
- `isResolved == false` のスレッドのみ抽出
- 各スレッドの全コメントを時系列で表示（最後の発言者の意図を読み取るため）
- 表示項目: コメント原文、コメント者、該当ファイル、該当行番号、URL

**2. Review body (総評コメント)**
- `body`が非空のものを抽出
- PR著者自身のreviewは除外してよい
- ボット（`login`が `[bot]` 終端、`gemini-code-assist`、`vercel`、`dependabot` など）は別枠で表示し、人のコメントと混ぜない
- 解決済みかどうかGitHub側で判別できないため、**全件を対応要確認として扱う**
- 表示項目: 本文、author、state（APPROVED/COMMENTED/CHANGES_REQUESTED/DISMISSED）、URL

**3. Issue comment (PR全体コメント)**
- ボット（vercel、gemini-code-assist、CI通知など）は除外または別枠表示
- 人のコメントで、PR著者以外のものを抽出
- 表示項目: 本文、author、URL

### 報告フォーマット

取得後、**3種類を区別して**以下の件数を報告する：

- 総Review thread数、未解決数、取得漏れの有無
- 総Review数、対応要確認のbody数（人のみ）、ボット件数
- 総Issue comment数、対応要確認数（人のみ）、ボット件数

### 終了条件

3種類のいずれにも対応要確認コメントが無い場合のみ「対応すべきコメントはありません」と伝えて終了する。**reviewThreadsだけを見て終了してはいけない**。

---

## Step 3: 各指摘の妥当性を実コードで検証して判断する

取得した対応要確認コメントそれぞれについて、**指摘内容が妥当か（＝コードを修正すべき正当な根拠があるか）を判断する**。1件ずつユーザーに修正可否を尋ねることはしない。

判断は必ず**実コードを読んで行う**。コメントは真実ではなくヒントにすぎない。コメントの主張が現在の実装・仕様と矛盾していないか、すでに対応済みでないかを実コードで検証する。ボットコメントも人のコメントと同じ基準で妥当性を判断する。

各指摘を以下のいずれかに分類する：

- **自動修正する（妥当）**: 指摘内容が明確で、実コードに照らして修正すべき正当な根拠があり、修正方法が一意に定まるもの。バグ指摘、明確な改善提案、規約違反の指摘など。
- **自動修正しない**: 以下のいずれかに該当するもの。これらは修正せず、Step 5 のサマリーで根拠とともに報告し、ユーザーの判断を仰ぐ。
  - **妥当でない**: 実コードを検証した結果、誤った指摘・既に対応済み・現仕様として正しい、などと判断できるもの（根拠を必ず添える）
  - **方針判断が必要**: 質問・議論・設計提案など、修正方法が一意に定まらない、あるいは方針の選択を要するもの
  - **意図が不明確**: 指摘内容から意図を読み取れないもの

---

## Step 4: 妥当な指摘をすべて自動的に修正する

Step 3で「自動修正する」と判断したすべての指摘を、**ユーザーへの事前確認なしにまとめて修正する**。

- 各指摘に基づいた修正を実施する
- 修正が他の箇所に波及する場合も、妥当な範囲で必要な修正をあわせて行う
- プロジェクトのコーディング規約とコード品質を維持する
- 修正後は変更したファイル全体を読み返し、矛盾が生じていないか確認する

### 同じ修正が必要な他の箇所も探して直す

**指摘された箇所だけを直して終わりにしない。** 同じ問題は他の箇所にもあることが多く、残すと次のレビューで同じ指摘を受ける。
各指摘について次を行う。

1. 指摘が指す問題を一般化する（例: 「この関数の戻り値のエラーを無視している」→「同じ関数を呼んでいる箇所すべて」）。
2. `Grep` で探す。修正前のコードにあった識別子、呼び出し、リテラル、構文の形を手がかりにする。
   指摘されたファイルの中だけで終わらせず、リポジトリ全体を対象にする。
3. 見つかった箇所を、このブランチの差分内か差分外かで分ける（`git diff --name-only origin/{baseRefName}...HEAD` と実際の行で判断する）。
   - **差分内**: このブランチが持ち込んだ問題なので、指摘された箇所と同じ修正を行う。
   - **差分外**: 既存コードの問題であり、直すとPRの目的から外れた差分が増える。修正せず、Step 5 で場所と内容を報告してユーザーの判断を仰ぐ。

---

## Step 5: 完了サマリーを提示する

すべての処理が完了したら以下を提示する：

- **自動修正した指摘の一覧**: 指摘内容 → 対応内容、修正ファイル
- **自動修正しなかった指摘の一覧**: 各指摘と、修正しなかった理由（妥当でないと判断／方針判断が必要／意図が不明確）。妥当でないと判断したものは根拠を明示する
- **指摘されていないが同じ修正を行った箇所**: 場所と修正内容、および検索に使った語と対象範囲。同種の箇所が無かった場合もその旨を書く。省くと、探した結果無かったのか探していないのかをユーザーが区別できない
- **差分外にあるため直さなかった同種の箇所**: 場所と内容を挙げ、このPRで対応するかをユーザーに尋ねる
- 自動修正しなかった指摘について、ユーザーに対応方針を尋ねる
- 次のステップの提案（コミット方法など）

> コミットの実行はユーザーの明示的な指示がある場合のみ行う。

---

## 注意事項

- **3種類のコメント（reviewThreads / reviews.body / comments）をすべて取得すること**。`reviewThreads`だけを見ると、レビュー総評（`#pullrequestreview-XXX`）に書かれた設計提案などを見逃す。過去にここで見逃しが発生した。
- 修正前に必ず実コードを読み、指摘が現在の実装に対して妥当かを検証する。コメントは真実ではなくヒントとして扱う。
- 妥当でないと判断した指摘を黙って無視しない。**必ず根拠とともにStep 5のサマリーで報告する**。
- 妥当性の判断が割れる・意図が不明確な指摘は自動修正せず、ユーザーに確認する。憶測で修正を進めない。
- 修正が他の部分に影響を与える可能性がある場合は、サマリーでその旨を明示する。
- プロジェクトのコーディング規約とコード品質を維持する。
- `git push` は使用しない。
