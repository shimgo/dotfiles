# 機能追加 Issue 作成スキル

機能追加・既存機能の仕様変更の要件を定義し、決まったフォーマットで GitHub Issue を作成する。

この Issue は、実装者とレビュアーが要件を判断する根拠になる。そのため、推測で書いた記述と、セクション間で矛盾する記述を残さない。

実装はしない。Issue を作成するだけである。

## 手順

### Step 1: フォーマットを読む

このスキルのフォルダにある `assets/issue-template.md` を Read で読む。Issue はこのフォーマットで書く。

- 見出しがコメントアウトされていないセクションは必須である（例: 「現状」「不変条件」）。
- 見出しごとコメントアウトされているセクションは任意である（例: 「経緯」「非機能要件」）。
- 各セクションのコメントは、そのセクションに書く内容の説明と例である。

### Step 2: 調べられることを先に調べる

ユーザーに質問する前に、依頼文、会話、渡されたリンク（Slack、PR、Issue）、コードから分かることを調べる。調べれば分かることを質問すると、ユーザーの手間が増えるためである。

- 「現状」は実装を読んで書く。関連する実装、テスト、DBスキーマ、GraphQLスキーマを確認する。
- コードコメントやドキュメントの記述は、実装と一致していることを確認してから使う。
- 調べた結果とユーザーの説明が食い違う場合は、根拠（ファイルパスと行番号）を示してユーザーに確認する。

### Step 3: 必須セクションが埋まるまで質問する

Step 2 で埋まらなかった必須セクションについて、ユーザーに質問する。すべての必須セクションに書く内容が決まるまで、質問を繰り返す。

- 推測で埋めない。ユーザーの回答、コード、本番データのいずれかを根拠にできる内容だけを書く。
- 質問には番号を振る。選択肢がある場合は選択肢に記号を振り、推奨する選択肢とその理由を示す。ユーザーが「1: a, 2: c」のように答えられる形にする。
- ユーザーの回答に同意できない場合（コードと食い違う、他のセクションと矛盾するなど）は、根拠を示して指摘する。
- 「不変条件」や「サポートしないユースケース」のように、ユーザーが自分からは挙げにくい項目は、コードを調べて候補を挙げ、採否を質問する。

質問の例:

```
1. 一部の商品だけを返品した場合、付与済みポイントはどう扱いますか？
   - a: 返品金額に応じたポイントだけを取り消す（推奨。理由: 〜）
   - b: 付与済みポイントをすべて取り消す
   - c: この Issue ではサポートしない
```

### Step 4: 本番データを根拠とする記述を検証可能にする

本番データを根拠とする記述（件数、存在の有無、発生頻度など）には、必ず次の形式でクエリと実行結果を添える。読み手が同じクエリを実行して、記述を検証できるようにするためである。

````markdown
<details>
<summary>本番でのxxxxの計測詳細</summary>

**xxxxの取得結果（yyyy-mm-dd hh:mm:ss JST 時点）**

x件

**計測クエリ**
```sql
SELECT ~
```
</details>
````

- クエリは Claude が書く。DBスキーマを確認し、実在するテーブルとカラムだけを使う。
- 実行結果を作らない。ユーザーが実行手段を指示していない場合は、クエリをユーザーに示して実行を依頼し、結果と実行日時を受け取る。
- ユーザーが実行手段を指示した場合も、実行するのは読み取りのクエリ（SELECT）だけにする。
- 結果を得ていない内容は、事実として Issue に書かない。
- 本番データでは確認できない事前条件（操作時にアプリケーションが検証する条件など）は、クエリを書かない。確認できない理由と、その条件を何で保証するかを書く。

### Step 5: 下書きを書く

フォーマットの各セクションのコメントに従って書く。加えて次を守る。

- 必須セクションは省略しない。この Issue では対象外である場合、または書く内容がない場合は、「なし」「対象外」と書き、そう言える理由も書く。理由がないと、検討した結果として「なし」なのか、検討していないのかを読み手が区別できないためである。

  例:

  ```markdown
  ### 既存データの扱い

  対象外。この Issue で追加する point_cancellations テーブルは新規のテーブルであり、リリース前に作成されたデータは新しいロジックの対象にならないため。
  ```

- 任意セクションは、書く内容がある場合だけ書く。書く内容がない場合は、見出しも書かない。
- フォーマットの説明用のコメント（`<!-- -->`）は Issue に残さない。
- Issue 単体で内容が完結するように書く。セッション中の会話を読まないと理解できない記述（「先ほどの案」「選択肢a」など）を書かない。リンクを張る場合も、リンク先の要点を Issue に書く。
- 番号だけで物事を指さない。「不変条件1（ポイント残高は履歴の合計と一致する）」のように内容を併記する。
- 計算の例では、同じ数値を重複して使わない。どの値がどの項を指すかを読み手が区別できなくなるためである。

### Step 6: Issue 全体を見直す

下書きを最初から最後まで読み直し、次を確認する。問題が見つかった場合は修正し、修正後にもう一度全体を読み直す。ユーザーの判断が必要な矛盾は、Step 3 の形式で質問する。

- 必須セクションがすべてあり、「なし」「対象外」には理由がある。
- 「現状のままでは困ること」の各項目が、「どうやって解決するか」で解決されるか、「この Issue では解決しない課題」に書かれている。
- 「どうやって解決するか」と「サポートするユースケース一覧」の範囲が一致している。
- 「サポートしないユースケース一覧」のうち課題として残る行に対応する課題が、「この Issue では解決しない課題」にある。逆に、「この Issue では解決しない課題」のうちユースケースに当たる課題が、「サポートしないユースケース一覧」にある。
- 「この Issue では解決しない課題」の各課題に、課題をどうするかの判断と、この Issue での対応が書かれている。
- 各不変条件が、サポートするどのユースケースの前後でも成り立つ。
- DBの制約で保証する不変条件が、「DBスキーマの変更内容」に併記されている。
- 「事前条件」「既存データの扱い」「確定した事実」の記述が互いに矛盾しない（例: 事前条件を満たさない既存データが本番にあるのに、「既存データの扱い」が「なし」になっていない）。
- 「確定した事実」に、事前条件の確認結果を重ねて書いていない。
- 本番データを根拠とする記述のすべてに、Step 4 の形式のクエリと実行結果がある。
- 同じものを、最後まで同じ用語で呼んでいる。
- フォーマットの説明用のコメントが残っていない。
- セッションの内容を知らない人が、Issue だけを読んで理解できる。

### Step 7: ユーザーの承認を得て Issue を作成する

1. 題名と下書きの全文をユーザーに示し、承認を得る。Issue は作成した時点で他の人に通知され、取り消しにくいためである。ユーザーが題名を指定していない場合は、解決策の内容を表す題名を提案する。
2. ユーザーが修正を求めた場合は修正し、Step 6 の見直しをもう一度行う。
3. 「この Issue では解決しない課題」に「別Issueを作成して解決する」と判断した課題がある場合は、別Issueを今作成するかをユーザーに質問する。作成する場合は別Issueを先に作成し、その Issue へのリンクを下書きに書く。
4. 本文を一時ファイルに書き出し、`gh` で作成する。Assignee には自分（`@me`）を設定する。

   ```bash
   gh issue create --title "<題名>" --body-file <本文のファイル> --assignee @me
   ```

   - 作成先は、カレントディレクトリのリポジトリである。ユーザーが別のリポジトリを指定した場合は `--repo <owner>/<repo>` を付ける。
   - ラベルとマイルストーンは、ユーザーが指示した場合だけ設定する。
5. 作成した Issue の URL をユーザーに伝える。
